## 1. 마인드셋: 게임 서버 엔지니어링의 본질

게임 서버 개발자는 **"눈에 보이지 않는 곳에서 시간과 공간의 불일치를 다루는 건축가"**입니다.

* **절대 클라이언트를 신뢰하지 않는다 (Zero Trust)**:  
  클라이언트는 메모리 조작, 패킷 변조, 프레임 드랍이 일어날 수 있는 불안정한 환경입니다. 중요한 판단(돈, 생성, 처치, 판정)의 권한은 무조건 서버가 가집니다.
* **시간(Latency)을 인정하고 제어한다**:  
  빛의 속도와 인터넷 회선 한계로 인해 모든 유저는 서로 다른 시간대의 세계를 보고 있습니다. 이를 부드럽게 맞추는 것이 서버 개발자의 숙명입니다.
* **동시성(Concurrency)과 메모리 수명에 집착한다**:  
  싱글스레드에선 절대 일어나지 않는 데드락, 경합 조건, 댕글링 포인터를 사전에 설계로 차단해야 합니다.

## 2. STEP 1. 3대 필수 기초 체력

서버 코드를 작성하기 전, 반드시 아래 3가지 분야의 밑바탕이 튼튼해야 합니다.

### ① 모던 C++ (C++17 / C++20)
* **스마트 포인터와 메모리 소유권**: `std::shared_ptr`, `std::weak_ptr`, `std::unique_ptr`의 내부 원리와 순환 참조(Circular Reference) 회피.
* **`std::enable_shared_from_this`**: 비동기 I/O 콜백에서 세션 객체 자신의 수명을 안전하게 연장하는 패턴.
* **RAII 패턴**: 생성자에서 자원을 잡고 소멸자에서 해제하는 원칙 (`std::lock_guard`, `std::unique_lock`).
* **메모리 정렬과 패딩**: 네트워크로 구조체를 그대로 쏠 때 `#pragma pack(push, 1)`을 왜 써야 하는지 이해.

### ② 운영체제 (Windows OS & 멀티스레딩)
* **유저 모드 vs 커널 모드**: 시스템 콜(System Call)과 컨텍스트 스위칭(Context Switching) 비용.
* **프로세스 vs 스레드 메모리 구조**: 코드, 데이터, 힙(공유) vs 스택(독립).
* **동기화 객체 (Synchronization Primitives)**:
  * 유저 모드: `CRITICAL_SECTION`, `std::mutex`, `std::atomic` (가볍고 빠름)
  * 커널 모드: `Mutex`, `Semaphore`, `Event` (프로세스 간 공유 가능, 느림)
* **데드락(Deadlock)의 4대 조건**: 상호 배제, 점유와 대기, 비선점, 환형 대기.

### ③ 컴퓨터 네트워크 (TCP/IP & Winsock)
* **TCP vs UDP의 근본 차이**: 신뢰성/순서 보장/흐름 제어 vs 빠른 전송/헤더 경량화.
* **TCP 3-Way Handshake & 4-Way Handshake**: 연결 수립과 종료 과정.
* **스트림(Stream)의 특성**: TCP는 데이터의 경계(Boundary)가 없다는 점을 뼈저리게 인식해야 함.
* **Nagle 알고리즘과 `TCP_NODELAY`**: 작은 패킷 딜레이와 실시간 게임의 관계.

## 3. STEP 2. 소켓 모델의 진화 과정 직접 체득하기

처음부터 바로 IOCP로 점프하면 왜 이 구조가 나왔는지 이해하지 못합니다. 아래 4단계를 **직접 코드로 구현해 보며 한계를 느껴보는 것**이 최고의 공부법입니다.

```
1. 블로킹 소켓 (1 클라이언트 = 1 스레드)
   └─ 한계: 동시 접속자가 1,000명이면 스레드도 1,000개? 극심한 메모리 낭비와 컨텍스트 스위칭 렉!
   
2. 넌블로킹 소켓 + select() 모델 (동기 다중화)
   └─ 한계: 한 스레드가 수천 개 소켓을 루프 돌며 검사(Polling). 접속자가 많아질수록 O(N) 검사 비용 폭증!
   
3. Overlapped I/O 모델 (비동기 I/O)
   └─ 발전: 커널에 "수신 끝나면 알려줘" 하고 내 할 일 함. 하지만 이벤트 핸들 제한(64개) 존재.
   
4. Windows IOCP (I/O Completion Port - 최종 완성형)
   └─ 혁신: 완료된 I/O 작업만 커널 큐에 쌓이고, 소수의 고정된 Worker Thread(CPU 코어 수 기반)가 
           큐에서 일감을 꺼내 처리. 컨텍스트 스위칭 최소화 및 수만 명 동시 접속 지원!
```

## 4. STEP 3. 나만의 `ServerCore.lib` 프레임워크 제작 순서

다음 프로젝트에서 혼자 처음부터 서버를 짤 때 따르는 **표준 구현 순서**입니다.

### [1단계] 코어 기반 인프라 구축
1. `Type.h` : 고정 크기 자료형(`int32_t`, `uint16_t` 등) 선언.
2. `NetAddress` : IP 문자열과 포트를 윈도우 소켓 주소 구조체로 감싸는 클래스.
3. `IocpCore` : `CreateIoCompletionPort`로 IOCP 핸들 생성 및 감시 함수 래핑.
4. `IocpEvent` : `OVERLAPPED` 구조체를 상속받아 I/O 작업 종류(Accept, Recv, Send, Disconnect)를 구별하는 구조체.

### [2단계] 세션과 버퍼링 완성
1. `Session` 추상 클래스 :
   * 소켓 핸들 보유.
   * `WSARecv`를 걸어두는 비동기 파이프라인.
   * 가상 함수 제공: `OnConnected()`, `OnRecv()`, `OnSend()`, `OnDisconnected()`.
2. `RecvBuffer` (슬라이딩 윈도우) :
   * `readPos`와 `writePos`를 두어 데이터가 덜 오면 기다리고, 뭉쳐서 오면 잘라내는 핵심 버퍼.
3. `Listener` :
   * 특정 포트를 리슨하고 클라이언트 접속 시 새 `Session`을 만들어 IOCP에 등록하는 수락기.

### [3단계] 프로토콜 및 패킷 시스템 설계
1. 패킷 헤더 정의:
   ```cpp
   #pragma pack(push, 1)
   struct PacketHeader {
       uint16 size; // 패킷 전체 크기 (헤더 포함)
       uint16 id;   // 패킷 종류 식별자
   };
   #pragma pack(pop)
   ```
2. `PacketType.h` : `C_LOGIN`, `S_LOGIN_OK`, `C_MOVE` 등 열거형 정의.
3. `Protocol.h` : 송수신할 구체적인 패킷 구조체 정의.
4. `PacketHandler` : 헤더의 `id`를 보고 알맞은 처리 함수로 분기하는 switch-case 디스패처.

### [4단계] ★ 에코(Echo) 핑퐁 테스트
* 게임 로직을 한 줄도 넣지 않은 상태에서, 클라이언트가 보낸 텍스트를 서버가 그대로 돌려주는 에코 테스트를 먼저 완벽히 성공시킵니다.

## 5. STEP 4. 게임 콘텐츠와 서버 권한형 동기화 설계

에코 서버가 성공했다면, `ServerCore` 위에 게임 규칙을 얹습니다.

### 1. 세션 상속 (`GameSession : public Session`)
* `playerId`, 유저 지갑(`gold`), 속해 있는 방 포인터(`std::weak_ptr<GameRoom> room`) 등을 추가.

### 2. 룸 아키텍처 (`GameRoom` & `GameRoomManager`)
* 방 안에서 일어나는 모든 상태 변경은 방 전용 뮤텍스(`std::mutex lock`)로 보호합니다.
* 유저 입장(`Enter`), 퇴장(`Leave`), 전체 전송(`Broadcast`)을 구현합니다.
* 다중 방 관리를 위해 `GameRoomManager`가 대기 중인 방(1/2)을 찾아 배정합니다.

### 3. 서버 권한형(Server-Authoritative) 단일 진실 공급원 (SSOT)
* **구매/건설 검증**:
  * 클라: "타워 지을게요" (`C_BUILD`)
  * 서버: 지갑 확인 (`gold >= cost`) ➔ 차감 ➔ 확정 결과 전원 방송 (`S_BUILD(remainingGold)`)
* **처치 및 사망 멱등성 (Idempotency)**:
  * 클라: "이 몬스터 체력 다 닳았어요" (`C_KILL(monsterId)`)
  * 서버: `std::set<int32_t> deadMonsters`에서 중복 여부 확인 ➔ 최초 1회만 승인 후 보상 브로드캐스트 (`S_KILL`)

## 6. STEP 5. 치명적인 동시성 함정과 디버깅 노하우

### ⚠️ 함정 1. 비재귀 락 데드락 (Self-Deadlock)
* **상황**: `GameRoom::Leave()`에서 `std::mutex`를 잡은 채로 상대방 세션의 `Disconnect()`를 호출함.
* **원인**: `Disconnect()`가 동기 콜백 `OnDisconnected()`를 부르고, 이것이 다시 `Leave()`에 진입하여 동일 스레드가 비재귀 락을 또 잡으려다 서버 크래시.
* **해결 원칙**: **"락(Lock)을 쥔 채로 외부 객체의 함수나 콜백을 절대 호출하지 말 것!"**  
  데이터 수집만 락 안에서 끝내고, 락을 완전히 해제(`unlock`)한 후에 소켓 함수를 호출해야 합니다.

### ⚠️ 함정 2. 비동기 I/O 도중 객체 자폭 (Dangling Pointer)
* **상황**: 패킷 수신 대기 중 유저가 강종하여 세션 포인터가 메모리에서 날아감.
* **해결**: `shared_from_this()`를 I/O 이벤트에 바인딩하여, 비동기 작업이 끝날 때까지 참조 카운트(Ref Count)를 유지.

### ⚠️ 함정 3. 패킷 파편화와 버퍼 오버플로우
* **해결**: 패킷 크기(`size`)가 현재 버퍼에 쌓인 데이터보다 크면 절대 파싱하지 않고 다음 `recv`를 대기할 것.
