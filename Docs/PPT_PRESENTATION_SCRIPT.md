## [SLIDE 12] 05 DETAIL 주요 기능 상세 01 : A* 동적 길찾기 & 미로 봉쇄 방지

### ⚠️ 이슈 (Issue)
* 유저가 타워를 자유롭게 건설하여 미로를 설계하는 과정에서, 몬스터의 이동 경로를 100% 틀어막을 경우 몬스터가 멈춰버려 게임 진행이 불가능해지는 심각한 결함 발생.

### 🛠️ 구현 방식 (Implementation)
* 터렛(2x2) 설치 요청 좌표를 그리드에 가상 배치한 뒤 A* 시뮬레이션을 수행(Dry-Run).
* 스폰 지점(S)부터 아지트(D)까지의 유효성뿐만 아니라, **현재 맵에 생존해 있는 모든 몬스터의 현재 위치에서 아지트까지 도달 가능한 경로가 존재하는지 전수 검증**.
* 단 하나의 몬스터라도 경로가 끊기면 설치를 기각(Rollback)하고 UI에 빨간색 경고 표시.

### 🎯 결과 (Result)
* 악의적인 길막 플레이를 원천 방어하고, 유효한 타워 설치 시 맵 상의 모든 몬스터가 새 경로를 즉각 재계산(`RecalculatePath`)하여 지능적인 미로 우회 플레이 완성.

## [SLIDE 13] 05 DETAIL 주요 기능 상세 02 : Windows IOCP & 서버 권한형 아키텍처

### ⚠️ 이슈 (Issue)
* 동기 블로킹 소켓은 클라이언트 프레임 정지를 유발하고, 클라이언트가 골드나 처치를 직접 판정하면 메모리 변조 취약점 및 두 플레이어 간 상태 불일치가 필연적으로 발생함.

### 🛠️ 구현 방식 (Implementation)
* **Windows IOCP 커널 완료 포트**를 기반으로 4개의 Worker Thread 풀을 구동하여 네트워크 I/O 오버헤드를 완벽히 분리.
* 슬라이딩 윈도우 `RecvBuffer`로 TCP 패킷 파편화를 방어하고, 모든 골드 잔고와 타워 유효성 판정을 서버 `GameRoom`을 **단일 진실 공급원(SSOT)**으로 삼아 처리.

### 🎯 결과 (Result)
* 60 FPS 무지연 콘솔 렌더링 유지, 클라이언트 메모리 변조 무력화 및 네트워크 지연 상황에서도 두 클라이언트의 인게임 상태가 100% 동기화됨.

## [SLIDE 14] 05 TROUBLESHOOTING 01 : 몬스터 처치 불일치 및 40골드 오차 버그

### 01. 문제 정의
* 30마리 웨이브를 양쪽 플레이어가 모두 완파했음에도 불구하고, 호스트는 300G인 반면 게스트는 260~290G만 적립되며 한쪽 클라이언트에서 적이 죽지 않고 배회하는 현상 발생.

### 02. 사실 수집
* 총알 히트 판정이 각 클라이언트 로컬에서 독립적으로 실행됨.
* 미세한 프레임 틱 오차로 인해 A 클라이언트에서 먼저 죽은 몬스터가 B 클라이언트에서는 아지트에 닿거나 타워 공격 틱이 엇갈려 로컬 판정 분기가 일어남.

### 03. 원인 추론
* 몬스터의 생사 여부와 처치 보상 지급 권한이 서버에 없고 클라이언트 분산 판정에 의존하여, 분산 시스템의 합의(Distributed Consensus)가 완전히 깨짐.

### 04. 조치 방안
* 스폰 시 몬스터에 고유 `monsterId`를 태깅.
* 체력이 0이 된 클라이언트는 로컬 골드를 직접 올리지 않고 `C_ENEMY_KILL(monsterId)` 패킷만 서버에 전송.
* 서버는 `std::set<int32_t> deadMonsters`를 검사하여 최초 1회 요청만 승인(멱등성 보장) 후, 방 전원에게 공통 골드 지급 및 `S_ENEMY_KILL` 브로드캐스트.
* **양 클라이언트 골드 오차 0원 및 몬스터 생사 100% 일치 달성.**

## [SLIDE 15] 05 TROUBLESHOOTING 02 : 파트너 강제 종료 시 재귀 락 데드락 및 서버 크래시

### 01. 문제 정의
* 2인 협동 플레이 중 한 플레이어가 게임을 강제 종료(Alt+F4 또는 창 닫기)했을 때, 서버가 정상 처리하지 못하고 서버 프로세스 전체가 치명적인 크래시(Crash)를 일으키며 다운됨.

### 02. 사실 수집
* 서버 콘솔에 `std::system_error: resource_deadlock_would_occur` 예외가 발생하며 `std::terminate()`로 강제 종료되는 로그 확인.

### 03. 원인 추론
* `GameRoom::Leave()` 함수가 `std::mutex lock`을 소유한 상태에서 퇴장 플레이어 정리 후 남아있는 파트너 세션의 `Disconnect()`를 호출함.
* `Disconnect()`가 동기식으로 세션 정리 콜백(`OnDisconnected`)을 호출하고, 이것이 다시 동일 스레드에서 `GameRoom::Leave()`에 진입하여 비재귀적 뮤텍스에 대한 이중 락(Self-Deadlock) 발생.

### 04. 조치 방안
* 락의 범위(Lock Granularity)를 최소화. 세션 리스트 제거 및 상태 갱신만 락 내부에서 수행하고, `lock.unlock()`으로 락을 완전히 해제한 뒤 파트너 세션 `Disconnect()`를 호출하도록 로직 분리.
* **파트너 비정상 이탈 시에도 서버 무중단 서비스 유지 및 남은 플레이어의 안전한 로비 복귀 완성.**

## [SLIDE 16] 06 RETROSPECTIVE 자체 평가 의견 및 회고

### 🏗️ 프로젝트 측면
* **완성도 높은 로우레벨 C/S 아키텍처 확립**: 단순히 상용 엔진 플러그인에 의존하지 않고, Windows IOCP 소켓 통신부터 자체 렌더링 엔진까지 직접 구축하여 시스템 레벨의 통제력과 네트워크 패킷 제어 역량을 확고히 증명함.
* **실전 분산 네트워크 트러블슈팅 경험**: 패킷 뭉침/쪼개짐, 분산 합의 불일치, 동시성 락 데드락 등 실제 상용 멀티플레이 서비스에서 마주하는 고난도 문제를 직접 재현하고 완벽히 해결함.

### 🧠 개인 측면
* **엔지니어링 사고방식의 체질화**: 문제가 발생했을 때 임시방편(Patch)으로 때우지 않고, "어느 스레드에서 락을 잡았는가?", "왜 두 노드의 골드가 차이나는가?"를 커널 및 패킷 레벨에서 파고드는 집요한 원인 분석 능력을 체득함.
* **설계 우선(Design-First) 원칙의 체득**: 코드를 작성하기 전 데이터 흐름, 스레드 경합 구역, 예외 시나리오를 먼저 정의하는 설계의 중요성을 절실히 깨달음.
